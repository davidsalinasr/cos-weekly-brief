# Chief of Staff Weekly Briefing

## Run sequence

Every invocation goes through these phases in order:

1. **Greeting & brief.** Always start with one short paragraph explaining what this skill does and that the user can adjust anything.
2. **Config check.** Look for `config.json` next to this file. If missing or has unset fields → run **Onboarding**. Otherwise → skip to step 4.
3. **Onboarding** (first run only, or when user asks to reconfigure).
4. **Data collection → synthesis → delivery** (the main pipeline).
5. **Summary** of what was created, with links.

Never ask the user for IDs they wouldn't know off-hand. Always discover via the connected MCPs. Always propose sensible defaults the user can confirm with one yes.

## Repository layout & how this skill uses each file

This skill is a small repo. Here is how the files relate at runtime:

| File | Role | When the agent reads it |
|---|---|---|
| `SKILL.md` | This file. The runbook the agent follows top-to-bottom every invocation. | On every run. |
| `config.json` | Generated by onboarding. Holds the user's IDs, connected-tool flags, and preferences. Gitignored. | At the start of every run (Step 2). Written during Step 3. |
| `config.example.json` | Reference shape of `config.json` for advanced users who want to pre-populate. Never touched at runtime. | Never read by the agent at runtime. |
| `references/email-template.md` | Visual spec + HTML skeleton for the Monday email. Defines color palette, table styles, priority-tag formatting, section order, and the full HTML token-template. | **Step 6a only.** The agent reads it once, fills the tokens with synthesized data, and submits the result via `gmail_create_draft` with `contentType: "text/html"`. |
| `references/slack-format.md` | Format spec for the self-DM. Defines tone, length budget, emoji-prefix priority convention, and the message skeleton. | **Step 6b only.** Read once, then compose the message and send via `slack_send_message` (NOT the draft variant). |
| `references/docx-template.md` | Spec + `python-docx` code patterns for the Word document. Defines color palette, section order, table column conventions, helper functions for priority colors and stale-row shading. | **Step 6c only.** Read once, then write a short Python script that imports `python-docx`, follows the helper patterns, and saves the file to `config.delivery.workspace_path`. |
| `README.md` / `SETUP.md` / `LICENSE` / `.gitignore` | Repo metadata for GitHub. Not read by the skill at runtime. | Never. |

**Contract with the reference files.** Each `references/*.md` file owns a *visual / structural* concern; `SKILL.md` owns the *flow*. When in doubt about what the email should look like, the reference file is canonical. When in doubt about *when* or *whether* to do something, this file is canonical.

## Step 1: Greeting

Print this paragraph, adapted to the situation (slightly shorter on subsequent runs):

> "I'm building your weekly chief-of-staff brief. I'll scan the past 7 days across the tools you have connected — messages, email, calendar, meeting transcripts, CRM, and your project tracker — sort everything into P0/P1/P2 priorities, and deliver the result as an email draft, a Slack message to yourself, a Word document, an Excel tracking log, and tickets on your executive board. Takes 3–5 minutes. You can stop me any time, change which tools I scan, or tune the priority rules — just say so."

On runs after the first, shorten to a single line: *"Running your weekly brief — say 'reconfigure' to change settings or 'explain' for details."*

## Step 2: Config check

Read `config.json` (sibling of this file). The shape is:

```json
{
  "user": { "name": "", "first_name": "", "title": "", "company": "", "email": "" },
  "slack":      { "connected": false, "user_id": "", "dm_channel": "", "channels": [] },
  "email":      { "connected": false, "address": "" },
  "calendar":   { "connected": false, "primary_id": "" },
  "transcripts":{ "connected": false, "provider": "" },
  "crm":        { "connected": false, "provider": "", "pipeline_stages": [] },
  "tracker":    { "connected": false, "provider": "", "exec_project_key": "", "sprint_project_key": "", "cloud_id": "", "account_id": "" },
  "delivery":   { "workspace_path": "", "schedule": "Fri 17:00 local", "stale_deal_threshold_days": 5 }
}
```

If the file is missing or any of `user.email`, `delivery.workspace_path`, or at least one of the source `connected` flags is unset → run **Onboarding**.

If the user explicitly says "reconfigure", "change settings", "update brief config", or similar → run **Onboarding** regardless.

## Step 3: Onboarding

Goal: get the skill ready to run with **zero ID-pasting** by the user. Discover everything from connected tools; only ask the human for *decisions*, never for raw identifiers.

Run these batches in order, using `AskUserQuestion` for choices and prose questions for free-form answers. After each batch, save partial state to `config.json` so a mid-flow interruption is recoverable.

### 3.1 Who are you (one batch, four short prompts)

Ask: name, first name, title, company. Email comes from connected Gmail/MS365 — don't ask, discover.

### 3.2 Detect which tools are already connected

**Always start with detection, not interrogation.** Call `list_granted_applications` (or the host client's equivalent connectors-listing tool) to enumerate every MCP the user has already authorized. Then map each connected MCP to one of the six categories using the table below.

| Category | Recognized MCPs (any of these counts) |
|---|---|
| Messaging | Slack, MS Teams, Discord |
| Email | Gmail, Outlook / MS365 |
| Calendar | Google Calendar, Outlook Calendar |
| Meeting transcripts | Fathom, Granola, Fireflies, Otter, Zoom AI |
| CRM | HubSpot, Salesforce, Close, Pipedrive |
| Project tracker | Jira / Atlassian, Linear, Asana, ClickUp, Monday, Notion |

Present the result back as a single confirmation:

> *"I see you have **Slack, Gmail, Google Calendar, and Jira** connected — I'll use these. You don't have a meeting-transcript tool or a CRM connected. Want to add either, or skip those sections of the brief?"*

For each missing category, ask once whether the user wants to add it. Only ask about categories they don't already have. If yes, recommend the most common provider but offer alternatives:

> *"Common transcript tools are Fathom, Granola, Fireflies, Otter, and Zoom AI. Which do you use? I'll walk you through connecting it."*

When the user picks one, prompt for the connection (use the host client's connect-MCP flow) and pause until auth completes, then re-run `list_granted_applications` to confirm.

If the user says "none" or "skip" for a category, mark `connected: false` for that category in `config.json` and the brief will omit that section at runtime with a one-line footnote.

### 3.3 Auto-discover IDs (no user input)

Once each MCP is connected, query it directly:

**Messaging (Slack example)**
- Call the Slack identity / `whoami` equivalent to get the user's `id`. Save as `slack.user_id`.
- The self-DM channel is the channel where the user is the only member. Either fetch via the conversations endpoint filtered to the user, or open a self-DM and capture the channel ID. Save as `slack.dm_channel`.
- For channel suggestions, list channels the user is a member of, sort by recent activity (`last_message_ts`), and present the top 8 as a multi-select with the top 5 pre-checked. (See 3.4.)

**Email (Gmail / MS365)**
- Call the profile endpoint for the connected account. Save the address as `user.email` and `email.address`. Don't ask — confirm: *"I'll deliver the brief to alex@acme.com (the connected account). Sound right?"*

**Calendar**
- Call `list_calendars`, find the primary, save its ID. Confirm with *"I'll read events from your primary calendar. Want me to also include any others?"* and offer the list.

**Meeting transcripts (Fathom example)**
- Call `fathom_list_team_members` or the equivalent identity endpoint to confirm the connected user. No further IDs needed — the brief queries by the connected user automatically.

**CRM (HubSpot example)**
- Call `get_user_details` and `get_organization_details` to confirm the connected account.
- **Pull deal stages directly from the schema:** call `get_properties` for the `deals` object, find the `dealstage` property, extract the options. Each option has a label and a `probability`. Save the full ordered list as `crm.pipeline_stages`. Show the user: *"I detected your pipeline: Prospect (10%) → MQL (25%) → … → Closed Won (100%). Use this for weighted-pipeline calculations?"* — they confirm with one click.
- For Salesforce/Close/Pipedrive: same pattern — read the stages from the API, never ask the user.

**Project tracker (Jira example)**
- Call `getAccessibleAtlassianResources` → save the cloud ID.
- Call `atlassianUserInfo` → save the account ID.
- Call `getVisibleJiraProjects` → present the list. Ask two simple questions:
  - *"Which project hosts your engineering sprint?"* → pick from list → save as `tracker.sprint_project_key`.
  - *"Which project should I use for executive action items? If you don't have one, I can create a new project called 'Brief' for you."* → either pick or trigger creation via `createJiraIssue`'s parent project flow.
- For Linear: list teams via `teams` query, ask which is the engineering team, ask which project (or label) is for exec actions.
- For Asana/ClickUp/Monday/Notion: equivalent list-then-pick flow.

After this batch, the user has answered ~3 multiple-choice questions about their org structure and zero ID-paste prompts.

### 3.3.5 Executive-action board (offer to scaffold if missing)

After project-tracker discovery, check whether the user already pointed at a project for **executive action items** — the place where weekly P0/P1 items will land as tickets. This is distinct from the engineering sprint project.

If they didn't, ask one question:

> *"Do you want a dedicated board for the brief's P0/P1 tickets — the place I'll create trackable tasks every week? Or should I just surface them in the email and Slack outputs without auto-ticketing?"*

If they say **no auto-ticketing**, leave `config.tracker.exec_project_key` empty. Step 6e will be skipped at runtime.

If they say **yes**, brainstorm placement with them rather than just creating something. Walk through the trade-offs:

- **Visibility.** Should the board be private to them, visible to a small leadership group, or company-wide?
- **Mixing with other work.** Do they want exec items isolated in their own project (cleaner, separate notifications) or mixed into an existing project with a label/tag like `exec-action` (less overhead, fewer notifications)?
- **Naming.** What fits their org's vibe? Common picks: "Brief", "CEO Action Items", "Exec Tracker", "Office of the CEO", "Weekly Actions". Suggest 2–3 options and let them pick or write their own.
- **Provider-specific options:**
  - *Jira / Linear / Asana / ClickUp / Monday* — usually a new project is cleanest. Confirm the project key/ID with them.
  - *Notion* — could be a new database, a section of an existing executive page, or a kanban view filtered by tag. Ask which fits their workspace.

Once decided, create it via the appropriate MCP call (e.g. `createJiraProject` for Jira if available, or `createJiraIssue` parented to a new project for the simpler path; `linear_create_project` for Linear; equivalents elsewhere). Save the resulting key/ID into `config.tracker.exec_project_key`.

Show the user a confirmation: *"Created the **Brief** project in Jira (key: `BRIEF`). Every week I'll add P0/P1 tickets here. Sound good?"*

### 3.4 Style & cadence (always lead with a default — user confirms or tweaks)

For each setting, propose a sensible default and ask only "Use this or adjust?":

| Setting | Default | Rationale |
|---|---|---|
| **Schedule** | Friday 17:00 local | Prepares Monday morning |
| **Workspace folder** | `~/Documents/Weekly-Briefs/` | Created if missing |
| **Stale-deal threshold** | 5 days | Common heuristic; tunable |
| **Channels to scan** | The 5 channels with highest user activity over the last 30 days (auto-discovered above) | Dynamic, no copy-paste |
| **Priority rules** | The pre-baked P0/P1/P2 definitions in the next section | Most users keep defaults |
| **Tone** | "Concise, direct, action-driven. No fluff." | Tunable in `config.json` later |

Phrase each as a confirmation, e.g.: *"I'll save briefs to `~/Documents/Weekly-Briefs/` and run every Friday at 5pm local. Want to change either of those?"* — single Yes/Adjust answer, not a blank form.

### 3.5 Save & confirm

Write the assembled `config.json`. Show the user a one-screen summary of what's configured. Offer: *"Setup complete. Want to run your first brief now, or save the config and run it later?"*

## Default priority rules

These ship pre-configured. Surface them during onboarding ("here are my default rules — adjust or accept?"), and let the user override per setting in `config.json` under a future `priority` key.

**P0 (Act today/tomorrow):** Anything that costs money, loses a deal, or breaks a commitment if not addressed today. Wire transfers, deal deadlines, production issues, migration cutoffs, investor responses, legal paperwork.

**P1 (This week):** Clear deadline this week or blocking another person. Follow-ups due, demos, budget alerts, tax deadlines, bugs blocking integrations, stale high-value deals.

**P2 (Monitor):** In progress, no immediate action. Partnerships advancing, applications pending, early-stage stale deals, sprint tasks on track.

**Cross-reference rule:** If something appears in 2+ sources, bump priority up. If a Fathom commitment lacks a tracker ticket, surface it. If a CRM deal is stale AND has email follow-up needed, it's P1 minimum.

## Step 4: Data collection

Run all six scans in parallel where possible (subagents or batched tool calls). Skip any source where `connected: false`.

### 4a. Messaging (last 7 days)
- Search the configured channels for key terms: deals, blockers, launches, deadlines, urgent, escalation.
- Extract: decisions made, commitments given, blockers raised, sentiment signals.

### 4b. Email — `config.user.email` (last 7 days)
- Query `newer_than:7d` plus targeted searches for "urgent", "wire", "payment", "invoice", "deadline", "overdue", and any company-specific terms the user added during onboarding.
- Flag: external partner emails, investor comms, legal/finance items, vendor escalations.

### 4c. Calendar (upcoming Mon–Fri)
- List events on `config.calendar.primary_id` for the next work week.
- Identify meetings needing prep.

### 4d. Meeting transcripts (last 7 days)
- List meetings, fetch summaries.
- Extract action items, decisions, commitments by/to the user.
- Cross-reference with calendar — if a calendar meeting has a transcript, pull its action items.

### 4e. CRM deals
- Search for deals not Closed Won/Lost.
- Compute days since last activity; flag stale (>`config.delivery.stale_deal_threshold_days`).
- Compute weighted pipeline using `config.crm.pipeline_stages` probabilities.

### 4f. Project tracker
- **Sprint:** active sprint of `config.tracker.sprint_project_key`, status != Done.
- **Executive board:** all open issues in `config.tracker.exec_project_key`.
- Flag capacity risks (any assignee with 4+ open tickets or missed standups).

Apply the priority rules. Run the cross-reference check. Produce the master action list with sources for each item.

## Step 6: Deliver via 5 channels

For any source where `connected: false`, omit that section and add a one-line footnote: *"Skipped: [source] — not configured."* If `config.tracker.exec_project_key` is empty (user opted out of auto-ticketing), skip 6e entirely.

### 6a. HTML email draft

**Read `references/email-template.md` once before composing.** That file is canonical for:
- The exact color palette (`#1a1a2e` navy, `#dc3545` P0 red, etc.)
- The full HTML skeleton with section order: TL;DR → Decisions Needed → Sprint → Deal Pipeline → Key Calendar → Email Flags → Carried Forward → Footer
- The inline-CSS conventions (no `<style>` blocks — most email clients strip them)
- The exact stale-row pink (`#fce4e4`) and table header styles
- Tone tips (e.g. omit empty sections rather than printing "None")

**Procedure:**
1. Read `references/email-template.md`.
2. Take the HTML skeleton from that file. Replace each `{{token}}` with the synthesized data from Steps 4–5.
3. For empty sections, delete the heading + body entirely (don't leave empty placeholders).
4. Subject line: `Chief of Staff | Week of [Mon DD, YYYY]`.
5. To: `config.user.email`.
6. Submit via the email-MCP draft tool (e.g. `gmail_create_draft`) with `contentType: "text/html"`.

If the email-template file is missing or unreadable, fall back to a minimal plain-HTML version with the same section order, but warn the user in the final summary.

### 6b. Slack self-message

**Read `references/slack-format.md` once before composing.** That file is canonical for:
- The emoji-prefix convention (🔴 P0, 🟠 P1, 🔵 P2 — Slack doesn't render colors)
- The length budget (~30 lines max)
- Bold/italic markdown rules (`**bold**`, `_italic_`)
- The skeleton: Title → P0 list → P1 list → P2 bullets → Carried Forward → Footer pointing at the .docx and email
- Tone rules: strip non-load-bearing words, prefer verbs over nouns

**Procedure:**
1. Read `references/slack-format.md`.
2. Compose the message following the skeleton, drawing from the same synthesized data as the email but condensed to glance-readable.
3. Channel: `config.slack.dm_channel`.
4. Send via `slack_send_message`. **Do NOT use `slack_send_message_draft`** — drafts strip markdown formatting in most Slack MCPs and the message renders as a wall of text.

If messaging is configured for MS Teams or Discord instead of Slack, adapt the same skeleton to that platform's markdown conventions.

### 6c. Word document (.docx)

**Read `references/docx-template.md` once before generating.** That file is canonical for:
- Color constants (`NAVY = RGBColor(0x1A, 0x1A, 0x2E)`, etc.)
- Helper functions for priority-tag colored runs and stale-row cell shading
- Section order (more detailed than the email — adds Fathom Action Items + Sources & Methodology sections)
- Table column conventions per section
- Font + size defaults

**Procedure:**
1. Read `references/docx-template.md`.
2. Write a short Python script that imports `python-docx` and follows the helper patterns from the reference. Reuse the helper functions verbatim — they handle priority colors and stale-row shading correctly.
3. Output filename: `Chief-of-Staff-Brief-Week-[Mon-DD-YYYY].docx`.
4. Save to `config.delivery.workspace_path` (create the directory if it doesn't exist).
5. Build sections in the order specified in the reference, populated with the same synthesized data.

If `python-docx` isn't available, the npm `docx` library is an acceptable substitute — the reference file's structural rules apply equally.

### 6d. Excel tracking log (.xlsx)

This output has no separate reference file — its rules live entirely in this section.

- **Filename:** `CoS-Weekly-Tracker-[YEAR].xlsx` (use the current year).
- **Library:** `openpyxl` (Python).
- **Granularity:** ONE row per weekly report (not per topic).
- **Columns:** Report Date | Month | Week # | Year | Short Summary | Link to Doc | Decisions Made | Actions Took | Actions Carried Forward.
- **Append behavior:** if the file exists, read it first then APPEND a new row. Never overwrite previous weeks. If the file is new, create it with a dark navy header row (`#1A1A2E` fill, white text), auto-filter on the header range, and freeze panes at `A2`.
- **Formatting:** wrap text in all cells, set row height to ~130 to fit multi-line summaries.

### 6e. Executive-board tickets

Skip this step entirely if `config.tracker.exec_project_key` is empty.

**Procedure:**
1. For each P0 and P1 action item, search `config.tracker.exec_project_key` for an existing open ticket with overlapping keywords (use the tracker's search API, not just title match — body text counts).
2. If a near-duplicate exists, skip and note it for the summary instead of creating a new one.
3. If no duplicate, create a new ticket via the tracker's create-issue API:
   - Project: `config.tracker.exec_project_key`
   - Type: Task
   - Priority: Highest (P0) or High (P1)
   - Assignee: `config.tracker.account_id`
   - Title: short imperative phrase from the action item
   - Description: full context including source links — e.g. `Source: Slack #general (link)`, `Source: email from sender@x.com (link)`, `Source: Fathom meeting (link)`
4. Collect the created ticket keys for the Step 7 summary.

## Step 7: Summary

After all deliverables exist, show:
1. Email draft link
2. Messaging-DM link
3. `.docx` file (`computer://` path)
4. `.xlsx` file (`computer://` path)
5. Tickets created (keys + titles)

Plus a one-liner: *"Say 'reconfigure' to change settings, or schedule the next run for [next Friday at 5pm]."*

## Important notes

- **Never ask for raw IDs.** If a value can't be auto-discovered, the right move is to connect the missing MCP, not to prompt the user.
- **Lead with defaults.** Every settings question should be a yes/adjust, not a blank form.
- **First run = full guided setup. Subsequent runs = silent, with a one-line greeting.**
- **Spreadsheet appends, never overwrites.**
- **When priority is unclear, err higher.**
- **Tone:** concise and action-oriented — the brief drives action, it doesn't summarize for its own sake.
